Executive summary — submitting this file

Everything you need is on this page. Total time: about three minutes, and one weekly submission slot.

Download first: ⬇ gems46-ridge-37k-ridge.tif ⬇ .zip (single GeoTIFF)

Step by step

  1. Sign in to DrivenData. Go to the competition page (competition 306, DOE GEMS Prize) and sign in with the account that owns the weekly slot. There is no separate submission portal.
  2. Open the submission form. Use the Submit / Upload a submission button on the competition page (the same page hosts the leaderboard tab). The form accepts a single file per slot.
  3. Choose the file. Upload gems46-ridge-37k-ridge.tif exactly as downloaded — do not re-encode, do not rescale, do not open and re-save it in QGIS or ArcGIS. The file is already in the exact contract format. If the form rejects a .tif for any reason, upload the .zip, which contains the identical GeoTIFF.
  4. Paste the name. 
    gems46-ridge-37k-v1
  5. Paste the note (199 characters, within the 200-character limit): 
    Unique 37,654-dot emission on a leave-one-anchor-out validated credit ridge (LOO Spearman +0.83); off-catalogue, no overlap with any prior GEMSDOE submission (max Jaccard 0.009).
  6. Submit and wait. Scoring is automatic; the public-leaderboard row normally refreshes within a few minutes. The score is computed against the withheld expert fault labels with the known USGS/INGENIOUS fault pixels masked out.
  7. Record the result — this is the important step. Append one row to data/anchor_manifest.csv with the returned score and a copy of the file in data/raw/anchors/, then re-run scripts/build_credit_model.py, scripts/build_credit_map.py and scripts/emission_search.py. The ridge model is built to consume every new (file, score) pair; the next submission is then fitted on N+1 anchors instead of N.

Why the earlier "values must be in [0, 1]" error happened

It is a format trap, not a modelling problem. GeoTIFF writers default to nodata = -3.4028234663852886e38 (the most negative float32). The portal validates every value in the file, including the sentinel, and rejects the upload. Setting the sentinel to zero or writing an alpha band does not always remove it; the robust fix is to never declare a nodata value at all and to clip the array to [0, 1] before writing. That is what this file does (src/gems46/rasters.py), and it is asserted by the verification script on every run.

What to do with the remaining slots

  • Slot spent on this file — record the score as anchor p46 (the next free id) and re-fit. If the score beats 0.2778 the emission direction is confirmed; if it lands below, the ridge direction is wrong at the top of its own range and the next slot should go to Hypothesis 3 (lidar scarps).
  • Next-best single file — Hypothesis 5's cheap variant, which needs no new data and no new model, only a different candidate set.
  • Never re-submit a file that already scored: the weekly budget is the scarcest resource in this competition.
